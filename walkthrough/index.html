Find the next measurement

Open Lounge in Unreal ↗ Launcher setup / project choices

Captured in Unreal · click an image to enlarge

Say

Stat unit gives us a lead. If GPU follows Frame, we inspect rendering work; if a CPU track follows Frame, we inspect its work and dependencies. A long scope can include waiting. Insights shows time across frames and queues. RenderDoc answers a different question: what draws, resources and pipeline state made one captured frame. Neither a colorful overlay nor an actor count tells us the time saved.

Show and do

  1. Show stat unit, then stat gpu. If needed set stats.MaxPerGroup 8 to keep the overview readable. Use stat RHI / stat scenerendering for the counters they actually name.
  2. Open the prepared Lounge-SM6 trace in UE 5.7 Insights. Click a frame, drag a time-ruler interval, press F. Read nested GPU events and graphics/compute overlap.
  3. Hide GPU tracks and follow a CPU wait to the work or pacing that ends it. The prepared trace used t.MaxFPS 60, so pacing waits are expected.
  4. Explain steady median versus p95 slow tail; p95 needs per-frame samples and a stated window. A transition hitch needs an event trace, not three HUD readings.
  5. Read pass families by responsibility: depth/PrePass establishes depth; Nanite VisBuffer handles visibility/raster work; BasePass evaluates surface outputs; ShadowDepths/VSM creates or updates shadow data; lighting applies light influence; Lumen/reflections traces and reconstructs lighting; translucency draws layered surfaces; post-processing/TSR produces the final/upscaled image. Inspect the actual trace names; these families are not guaranteed exclusive timing buckets.
  6. For memory inspect stat streaming, stat RHI, memreport -full, Size Map / Statistics and resource owners as appropriate. Object/resource snapshots, residency, cooked size and loading timelines are different evidence. Use stat initviews only for the conventional visibility counters it actually reports.
Evidence / acceptance

Name one relevant pass or CPU dependency and what further evidence would confirm it. GPU counters and inclusive totals are not a serial sum.

Reset: stat none; stats.MaxPerGroup 25. Close heavy diagnostic captures before the minimal timing run.

Time boundary: Use the prepared trace if live capture takes more than one minute. It includes startup and concurrent editor work; it is a navigation example, not the baseline for a saving claim.

Say

A texture has source data, cooked GPU data and currently resident mips. Those are different quantities. A smaller residency requirement can help memory without moving steady GPU time. We will inspect one expendable surface texture at the intended distance. Packing masks, removing alpha and resizing are separate operations; we will not combine them and claim a single cause.

Show and do

  3. Record format, resource size, mips, Max Texture Size / LOD Bias and current quality. If this is the selected experiment, lower one size limit by one step; wait for streaming and inspect near/far/moving views.
  4. Check readable detail, normal/roughness stability and mip edges. Record resource/residency evidence separately from frame timing. Leave compression, channel packing and pool budget fixed for this test.
Evidence / acceptance

A smaller resource is a memory result. r.Streaming.PoolSize changes a runtime budget, not cooked texture bytes.

Reset: Restore the original assignment or keep the changed texture only in the duplicate material. stat none.

Open Niagara in Unreal ↗ Launcher setup / project choices

From the slides · visual reference

Say

Bake replay, effect culling, screen coverage and pooling are different levers. VAT stores vertex motion; a flipbook stores images. GPU compute updates particle state, and a renderer turns that state into visible geometry. A dispatch is not a draw. Pooling reuses allocation and must reset the effect correctly.

Show and do

  1. Debris: use the prepared Modes Dynamic / VAT / Flipbook with identical timing and burst schedule. Inspect one burst first, front and side at sample 12. Timing uses 24 synchronized bursts and three launches per treatment with screenshots disabled; do not compare that load to the lounge.
  2. Use the supplied capture runner for separate visual and timing output directories. Check silhouette, onset, lifetime, depth and whether a new obstacle needs runtime response. A fixed card and baked motion have different failure cases.
  3. Niagara: inspect an existing Simple Sprite Burst, GPUComputeSim, Fixed Bounds, Solve Forces and Velocity, Particles.Position and Sprite Renderer. Trace simulation dispatch and rendering separately.
  4. Effect Type: hold camera, placement, spawn cadence and particle settings fixed. Compare distance culling OFF/ON, update frequency and cull reaction; count active systems and check re-entry. Spawn Only policy has a different lifecycle than continuous updates.
  5. Coverage: duplicate the system and change only spawn rate. Check density/motion and translucency work; lifetime/card size remain controlled. A show flag may hide drawing without stopping simulation.
  6. Pooling: replay identical impacts with Spawn/Destroy versus AutoRelease. Separate priming from reuse, inspect spawn-frame CPU and GC, count retained resources, and verify state reset after repeated cycles.
Evidence / acceptance

One changed mechanism, matched onset and a visual/interaction check. Do not sum historical effect savings or treat a source-card illustration as a local measurement.

Reset: Restore effect rates, policies and show flags. End all comparison processes.

Time boundary: Existing spawn-rate or distance-rule test 5–8 min after setup. New VAT authoring, bake generation or pooling implementation is separate preparation.

EXPLORE FURTHER · 10 MIN · SLIDES 20–31, 136–148, 162–163, 169

Hitches, PSOs, memory and regression checks

Captured in Unreal · click an image to enlarge

From the slides · visual reference

Say

A warm steady frame, a cold encounter and a streaming transition answer different questions. Shader compilation and graphics-pipeline creation are not the same event. A fresh process can reuse a warm driver cache. The result must describe its cache conditions and include the first visible frames, not just the quiet interval afterward.

Show and do

  1. Stage a Win64 Development package using Project Launcher or reviewed BuildCookRun settings. Record revision, target RHI/driver and quality. Smoke-test map, Audit Camera, logs and CSV outside the editor.
  2. For a hitch capture the same route with cpu/gpu/frame/bookmark plus appropriate loading, memory or counters channels. Inspect execution, waits and their dependencies. RenderDoc is for one frame’s draws/resources, not the full hitch distribution.
  3. Test PSO precaching/bundled cache coverage on the target API with documented cold/warm conditions. Inspect misses/late preparation, loading time, retained memory and pop-in; an editor success is insufficient.
  4. For World Partition or another streaming boundary, repeat the same movement, camera and state. Inspect loading and actor registration, resident memory, slow frames and visible pop. The furnished lounge is not a large-world streaming benchmark.
  5. A perf bot uses fixed workload, unique run directories, timeouts, raw logs/CSVs and repeated launches. Compare median and p95 to both absolute budget and a known-good baseline. Keep disagreeing runs and trace their slow intervals.
  6. Calibrate quality tiers to real scene/device data; hardware benchmark indices are not guaranteed FPS. Detail Mode may remove expendable content only; retain required cues and allow a player override.
Evidence / acceptance

In the deck’s example Frame 57.8 ms with GPU 6.1 ms suggests inspecting Render/RHI and waits, not declaring a slow GPU. The wait label alone still does not establish the cause.

Reset: Restore profiling settings and route state. Keep a unique build/run record and never replace the baseline with an unverified run.

Time boundary: Use prepared captures in the recording. Packaging, PSO validation and automation have variable duration and are not 5-minute fixes.

What each production example contributes

From the slides · visual reference

Say

These examples explain mechanisms and tradeoffs. Their workloads and measurements belong to the source games. They are not additional defects to inject into the lounge or savings to add to our benchmark.

Show and do

  1. Factorio (17): cache stable draw preparation and invalidate changed/newly visible data. Animated pixels can still change.
  2. DOOM (42): cluster relevant light/decal/probe lists. Large influence volumes can reach more clusters; shadows remain separate.
  3. Fortnite HLOD (57): distant proxy representations trade detail and culling granularity. LEGO (58): target-specific geometry/LOD/stud representations must preserve brick identity, including revealed undersides.
  4. Fortnite foliage (74): more opaque geometry can avoid masked coverage work in that content. Time the actual path and check silhouette/motion.
  5. Horizon clouds (102): skip empty density and vary sampling carefully; edges and temporal stability constrain it. Tsushima wind (108): shared procedural gusts and local interaction solve different motion needs.
  6. Pirates/material diversity (116): shading bins and capture overhead can matter independently of pixel arithmetic. Fortnite wind/VAT and Uncharted effects (119,124): shared transforms/per-vertex replay and bounds-aware cards have distinct data and viewpoint limits.
  7. Fortnite PSO preparation (139): move likely first-use work into loading, then test uncovered states and cold/warm behavior.
Evidence / acceptance

For every example name the work avoided, when the cached/baked/proxy result stops being valid, and the quality or memory trade.

Reset: No local project change.

Time boundary: Optional source recap; no added short-demo fix or claimed source speedup.
